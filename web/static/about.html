A working sample for your engineering role

Hi, I'm Nosa Omorodion. I built a small internal platform to show how I'd work.

Your post says you build internal systems to the same standard as public products: specified, tested, reviewed and observable. So instead of only sending a CV, I built one. Lighthouse is a Go service that joins three data sources into one account-health view. It has a dashboard for non-technical users, an LLM-written account brief, and a spec, tests and metrics to go with it.

What you asked for, and where to find it

From the job postIn this project
Design and deliver systems and platforms, including intuitive UIs One deployable binary: Go API plus an embedded dashboard. Filter, search and sort, a click-through account drawer, works on a phone, supports dark mode and keyboard use.
Build Go services and APIs that connect many data sources A Source interface with CRM (JSON), support desk (CSV) and analytics (column-shaped JSON) adapters. They are fetched concurrently, each with its own timeout and panic recovery, so one bad source can't stop the others. Uses only the Go standard library. internal/source, internal/aggregate
Design data models and architecture for connected systems Account is the root and tickets and usage reference it. Views are derived, never stored. Records that point at unknown accounts are dropped and reported, not hidden. internal/model, SPEC §5
Turn data into clear dashboards and visualisations KPI tiles, health distribution, weekly ticket trend, usage sparklines and per-account charts. Hand-built SVG, accessible labels, no chart library.
Build LLM-powered features into everyday workflows "Generate brief" on every account calls Claude with only the platform's facts. If there's no key or the call fails, it falls back to a rule-based brief. Briefs are cached per data version to keep cost down. internal/insight
Write specs, estimate work and deliver to agreed criteria docs/SPEC.md: problem, users, goals and non-goals, 10 requirements, each with acceptance criteria and the test that proves it, plus estimates and risks.
Set a high bar in code review, testing and documentation Table-driven unit tests, an httptest API suite, a fake Claude server, and timeout, panic and partial-failure tests. Run with go test -race ./.... Every package has doc comments that explain why.
Observable /healthz, /readyz (which reports stale data), Prometheus /metrics per route and per source, JSON logs with request IDs, and graceful shutdown.
Partner with non-technical colleagues to turn needs into tools The health score is explainable: every point lost shows a plain-English reason, so a CS lead can check it by hand and argue with the weights.

How I work

01

Spec first

Agree the problem, the users and what "done" means before writing code.

02

Small, tested steps

Every acceptance criterion maps to a test. Pure functions where possible.

03

Fail visibly

Partial data is shown as partial. Nothing gets dropped silently.

04

Own it in production

Health checks, metrics and logs ship with the feature, not after it.
